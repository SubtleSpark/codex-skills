# 知识回流 PR

从“当前共享知识需要新增、补充或纠正什么”出发，形成可独立理解的贡献。文件差异帮助寻找候选，不能直接当成待回流清单。

## 范围与授权

遵循用户本次要求和此前仍有效的授权。要求完成回流 PR 时，完成整理、验证、提交、推送和创建 PR，不逐步重复确认；只要求讨论或整理时，停在相应结果。缺少发布授权时，先准备可审阅改动，再只确认尚未授权的动作。创建 PR 不包含合并 PR、同步其他工作树或清理源工作区。

不预设机器路径、GitHub 账号、仓库名、远端名或目标分支名。使用当前环境已有的 Git、托管平台 API 或 CLI；缺少必要能力时报告限制，不自动安装工具、创建后台任务或另建状态数据库。

## 确认来源与目标

- 从任务上下文和实际 Git 状态确认来源；读取相关的已提交、暂存、未暂存和未跟踪材料。未跟踪文件不会出现在普通 diff 中。不要扩展成全磁盘或无关会话扫描。
- 优先采用用户已指定或任务中已确认的目标库。区分来源仓库与目标知识库，不能仅凭当前目录或 `origin` 推定目标。无法消除的目标歧义才需要询问。
- 读取目标库的贡献规则、入口和相关页面，遵循它的收录范围、证据要求及写入约定。项目专属知识按实际归属处理。
- 确認目标分支；用户未指定且库规则未规定时，使用远端默认分支。通过 fetch 或远端 API 取得它的最新提交及内容。读取最新主线不要求先把它合入源工作树。

## 提炼并整合知识

每项候选应能说明结论、适用条件、依据和对未来任务的作用。依据可以是可复查来源或有条件说明的实际观察，不能把 AI 共识、review 或 PR 合并当作事实证明。原始材料按目标库规则保存，不为整理方便改写原始证据。

对照目标分支当前内容、直接相关页面和相关未合并 PR：

| 情况 | 处理 |
| --- | --- |
| 本地落后或仍保留旧表述 | 识别版本差异，不作为新发现写回；新的反证仍须按证据评估。 |
| 主库已覆盖同一结论 | 跳过；仅换措辞不算新知识。 |
| 新增条件、证据、反例或边界 | 优先补充最接近的现有页面。 |
| 有依据的纠正 | 说明纠正的依据和影响，按库规则保留必要的纠正说明。 |
| 结论冲突 | 核对场景、版本和依据；条件不同就写清条件，无法判定就保留分歧与未知。 |

相关未合并 PR 是提案，不能视为主线事实。同一贡献已有 PR 时，在授权范围内继续完善；其他工作有重叠时说明依赖或分歧，不覆盖他人的改动。已合并 PR 只用于理解历史，去重以当前主线为准，因为内容可能已被改写、撤销或纠正。

没有合适增量时说明原因并结束，不制造空 PR。候选清单只服务本次整理，无需另存回流日志或队列。

## 组织贡献分支

默认在目标库最新目标提交上准备干净的短期贡献分支，使用安全且空闲的独立工作区或远端编辑能力。保留仍在使用的工作树；源任务可以继续长期运行。

如果已有任务分支的全部拟合入变化和拟推送历史都属于本次贡献，可直接复用。独立且完整的提交可以挑选过去；混杂改动应选择或重写。仅选择 stage 文件不会排除分支已有的无关提交，最终 diff 干净也不代表历史没有夹带其他材料。

在目标库当前页面上编辑，保留已有有效信息；不要整页复制旧工作树而覆盖主库的新内容。同步修复本次改动影响的链接和索引，成果应无需原任务上下文即可理解和核对。

回流本身不要求改写源树、提交源树全部内容或把 main 合回源树。不要为方便整理而自动 stash、reset、clean、rebase 或覆盖活跃任务。原任务需要同步时，按该任务的授权另行处理。

## 检查冲突并验证

分别检查两种冲突：
- **文本冲突**：用 Git 合并检查或托管平台可合并性检查，确认贡献分支与最新目标提交能否整合。必要时在贡献分支或隔离环境中试合并，保留双方有效内容。
- **知识冲突**：检查目标页面及直接相关结论是否重复、矛盾、过时或遗漏适用条件；Git 能自动合并不代表知识相容。

有充分证据就完成纠正；证据不足时可以提交明确记录分歧的文档变更，不能随意选一边写成确定事实。发现新结论会影响源任务正在使用的判断时，及时指出具体影响。

解决冲突后重新阅读最终页面和完整 diff，按目标库要求检查链接、索引、格式及必要验证。核对拟发布内容及提交历史，排除凭据、无关任务材料和不应公开的私人信息。

提交 PR 前复查目标分支及相关 PR。目标前移时重新检查文本合并，并复核受影响的知识；记录检查对应的目标和贡献提交。无法取得最新主线或完成关键检查时，不宣称无冲突；如需分享未完成结果，使用 Draft PR 并说明阻塞。

## 提交与反馈

遵循仓库的分支和提交习惯。PR 描述说明知识变化、依据、验证结果，以及仍存在的分歧或限制；不粘贴完整任务过程。

创建或更新 PR 后核实远端分支、目标和实际 diff；可用时将 PR 附加到当前聊天。推送或创建结果不明确时，先查询远端状态再重试，避免重复 PR 或覆盖并发提交。

若用户还授权合并，合并前重新确认最新目标与 PR head、冲突和必要检查；相关版本变化后重新验证。否则停在 PR。

反馈实际成果和 PR 链接，区分“已整理”“已提交 PR”“已合并”与“原工作树已同步”，只报告已验证的状态。
