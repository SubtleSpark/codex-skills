# 边界案例

以下场景用于校准判断，不是已执行的测试报告。未注明例外时，假设本会话其他要求、文件和 Git 处置均已检查并收尾。

| 场景与证据 | 整会话结论 | 报告要点 |
| --- | --- | --- |
| 本次修改已提交，约定验证已通过；起始记录证明剩余脏文件属于其他任务。 | 可归档 | 排除无关修改，不要求全仓库干净。 |
| Git 状态为空，但本会话早先约定的集成测试仍失败；后来的另一个任务已完成。 | 暂不建议归档 | 早先任务不会因最新任务完成而消失。 |
| 会话记录明确创建了已无用途的 `debug.log`，它仍存在且已被忽略。 | 暂不建议归档 | 建议删除；已忽略不代表生命周期已结束。 |
| 用户要求生成并保留 `.tmp/report.json`，文件已交付，现有规则已忽略。 | 可归档 | 保留交付物，不把生成文件当垃圾。 |
| 正式源码尚未提交；用户明确要求自行看 diff 后决定提交，任务未要求 Codex 提交。 | 可归档 | 说明有意保留未提交状态，不擅自提交。 |
| 正式源码尚未提交，且没有用户选择或仓库约定支持继续保留该状态。 | 暂不建议归档 | 建议处理本次有效变更，不能臆测“用户之后会提交”。 |
| `App.java` 混有多个任务修改，无法区分本会话部分是否已收尾。 | 需要确认 | 不建议整体提交、删除或回滚该文件。 |
| 一个无关目录中的文件只有时间戳接近本会话；无其他任务关联证据。 | 可归档 | 不仅凭时间戳认领，也不让无关疑问阻塞归档。 |
| 一个可能是本任务必需的 migration 文件缺乏来源和最终处置记录。 | 需要确认 | 指出具体交付风险及需要确认的问题。 |
| 用户只让检查任务 A 或 Git，检查通过，但同会话任务 B 未检查。 | 需要确认 | 只能说该部分未发现问题，不能据此判定整会话可归档。 |
| 已知本会话有遗留修改，但现在无法访问对应 worktree，或关键历史缺失。 | 需要确认 | 写明证据缺口，不把“查不到”说成“已干净”。 |
| 用户要求实现并提 PR 后交其 review；PR 已创建、工作已移交，本会话无剩余动作。 | 可归档 | 不要求 PR 合并；若约定的 PR 尚未创建则暂不建议归档。 |
| 当前是非 Git 目录；请求已完成，交付物明确保留，无临时文件遗留。 | 可归档 | 跳过 Git，不把没有仓库当成检查失败。 |
| 测试明确未完成，同时存在归属不明的本任务候选文件。 | 暂不建议归档 | 确定阻塞项优先，不确定项单列；不执行测试或清理。 |
