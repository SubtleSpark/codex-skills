# Session 归档前检查

只判断当前 session 的事是否做完、成果是否保存好、还有没有必须处理的后续。不要求整个 repo 干净，不做项目审计。

## 操作边界

除“可归档”时按下文规则 rename 当前 session 外，只读取可访问的历史、文件、Git、相关 session / 任务状态和已有验证结果；使用当前环境确实提供的能力。不修改或删除文件，不生成报告文件，不 stage、commit、stash、回滚、切换 branch、fetch、push 或 archive。不为补验证运行 test、build、format；不停止、重启或持续轮询后台任务。清理和补做任务只给建议，不在本次检查中执行。

## 1. 确定检查范围

按用户最新要求检查本 session 的全部任务，不只看最后一项。已取消、明确放弃、接受限制或明确移交且无后续责任的事项不再算未完成；说明去向即可。暂停等待仍属未完成；可选优化、未采纳的建议和项目原有 TODO 不算待办。

只检查操作记录指向的文件、repo / worktree，以及有创建记录或关系信息的相关 session 和后台任务。不扫描整个磁盘、无关历史或全部进程。只读过、没有改动的无关目录不用审计。历史截断、路径不可访问或关系不明时，只有缺口会影响结论才列“需要确认”，并说清缺什么。

用户只要求检查某个子任务或 Git 时，只报告该部分的结果，并写“局部检查；会话整体未评估”。不据此给整个 session 下结论或添加“可归档”标题。

## 2. 检查事情是否做完

以用户要求、实际操作、当前成果和对应版本的验证结果为准，不凭助手说“完成”、会话闲置或 `git status` 为空判断。约定的工作或验证未完成、失败仍未解决时，列为待处理；后续有效验证已解决的旧失败不再列出。

相关工作只检查当前 session 是否还有责任：

- **subagent session**：执行本任务的一部分；检查必需结果是否完成、已接收并满足约定验证。停止运行不等于完成。
- **independent session**：另行推进的独立任务；已明确移交且当前 session 无剩余动作，不必等它完成。仅创建新 session 或 PR 不代表移交；不能凭工具名称或共享目录判断关系。
- **后台进程、下载、远端异步作业**：按本次记录中的任务 ID、日志或状态接口，核对完成状态和所需结果。启动成功、进程退出或文件出现都不等于任务成功。只要求启动的长期服务、已明确移交且不再需要本 session 处理的作业，满足约定即可；仍需等待结果、集成或处理失败的任务不能算完成。关键状态无法核实时列“需要确认”，不要猜。

相关 session 已做完但尚未 archive，通常不影响当前 session；用户另有明确约定则按约定检查。不要猜测环境是否会连带 archive，也不要仅因不知道这一点而阻止归档。

## 3. 检查成果和文件

核对成果已按要求保存并可找到。根据操作记录、起始状态和具体 diff 判断归属；不凭文件名、时间戳或脏文件列表认领。混合修改只检查本任务的部分，不建议整体提交或回滚。

核对相关路径实际所属的 repo / worktree，包括本次改过的嵌套 repo、ignored 路径和 repo 外文件；外层 repo 干净不代表内层已完成。不是 Git 项目就跳过 Git 检查。

- **未 commit、未 push 或 PR 未合并**：本身不阻止归档，不要求用户额外声明保留未提交状态。只有本次任务或适用的仓库规则明确要求这些操作，或已有证据表明成果有丢失风险时，才列为必须处理。staged 不等于已 commit；不要假定 archive 会删除 worktree。
- **普通日志、一次性脚本和中间文件**：不影响交付时只给可选整理建议，不因此阻止归档。明确约定的清理未完成，或发现实际泄露、交付等风险时，才必须处理。生成文件、untracked 或 ignored 状态都不等于垃圾；保留有用途的成果。
- **标准缓存**：工具在标准目录维护的缓存、下载包和可复用运行时默认不检查、不建议删除；本次自定义缓存位置、写入任务目录或有具体异常时再定向查看。

Git 查询使用 `--no-pager --no-optional-locks -c core.fsmonitor=false`；路径用 `--literal-pathspecs` 与 `--` 传入，diff 加 `--no-ext-diff --no-textconv`。按需查看 status、暂存及未暂存 diff；untracked 内容另读，ignored 文件按已知路径查看。`check-ignore` 返回 1 只是未匹配规则。以当前状态为准，不拿旧检查代替已变化的内容。

## 4. 给出结论

完整检查按以下顺序判断：

| 结论 | 条件 |
| --- | --- |
| 暂不建议归档 | 有明确要求尚未完成，或本任务存在必须处理的具体成果丢失、泄露、交付风险。 |
| 需要确认 | 没有明确未完成事项，但缺少会影响归档判断的关键证据。 |
| 可归档 | 会话检查完成，没有上述问题；可以仍有可选整理建议。 |

明确未完成事项与疑问并存时，使用“暂不建议归档”并分别说明。只有局部检查时，按第 1 节报告，不套用整体结论。

先给结论和 1–2 句依据；有问题再列“待处理”，写清事项、当前状态和下一步。普通整理建议另列，并说明不影响归档，没有则省略。必要时附路径、任务 ID 或验证结果；未检查要如实说明，不写成“未发现问题”。不输出凭据或无关内容，不复述全过程，不为了填格式制造待办。遇到容易误判的情形时再读[边界案例](references/examples.md)。

结论为“可归档”且当前环境支持 session rename 时，将当前 session 标题改为 `可归档 | <原标题>`；已有该前缀时不要重复添加。只 rename 当前 session，不执行 archive。若环境不支持 rename，或 rename 失败，不改变 archive 结论，在“待处理”中简短提示手动加前缀。
